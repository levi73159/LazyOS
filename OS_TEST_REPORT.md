# LazyOs runtime test report

Date: 2026-10-23

## Tests performed and limitations

- **Boot and environment:** booted the existing kernel with OVMF in headless QEMU using q35, TCG CPU emulation (`max`), and 4 GiB RAM. No physical Intel/AMD hardware, KVM, or SMP coverage was established.
- **Real keyboard path:** used QMP keyboard events to run shell commands and send Ctrl+C through the emulated PS/2 keyboard and TTY. Checked both blocked input and a CPU-bound infinite loop.
- **Utility smoke tests:** launched `true`, `false`, `echo`, `cat`, `pwd`, `uname`, `ls`, and `stat`; inspected serial syscall traces. Returning to the shell is not proof of correct utility output or exit status.
- **Raw syscall probes:** compiled a small static test executable and ran 25 basic cases covering buffers, file descriptors, vectors, paths, stat metadata, mmap/munmap, brk, and basic rt_sigaction registration/querying. Additional probes tested user-fault isolation, Ctrl+C, null ioctl output, and SIMD preservation. Unique deliberately unsupported syscall numbers served as result markers in serial logs; those marker calls returning ENOSYS are expected test behavior.
- **Cleanup measurement:** counted set bits in the user physical allocator bitmap before and after twelve process exits, each leaving 64 KiB mapped. Compared snapshots after allowing cleanup to run.
- **Malformed inputs:** executed an ELF with PT_LOAD filesz greater than memsz; tried `run` without arguments; tested a valid sparse executable and verified its bytes independently with debugfs.
- **Register preservation:** compared XMM0 before and after raw getpid and ran the same probe on the Linux host as a control.
- **Isolation:** used temporary filesystem images and QEMU disk snapshots. Crashing cases ran in separate VMs or were followed by a fresh boot. No kernel or application source was modified.

**Result summary:** 36 recorded checks passed; eight utility launches completed; five distinct bugs were reproduced, counting the sparse-file finding from the initial run. One bitmap-reading attempt was inconclusive because of a harness quoting error; a corrected retry passed. Counts include repeated checks and do not represent 36 independent subsystems.

Not covered exhaustively: storage writes, long-running stress, all signal dispositions, custom signal handlers, out-of-memory recovery, all malformed ELF variations, device combinations, kernel-heap leakage, and concurrent/SMP behavior.

## Confirmed bugs

### 1. ioctl with a null output pointer panics the kernel

**Severity: High · Priority: P0 · Effort: Small–medium**

**Description and impact:** A syscall argument crosses the user/kernel boundary without request-specific memory validation. A valid TTY descriptor with a null output pointer reaches a Zig pointer conversion and takes down the entire OS. Failure should remain local to the requesting program as an errno result. The observed null-pointer panic is confirmed; additional corruption or privilege escalation was not tested.

**Fix scope:** determine the size and direction of each supported ioctl payload, validate the complete user range, and handle potentially unaligned addresses safely. Cover both getter and setter requests rather than patching TCGETS alone. Reject unsupported requests without touching their arguments.

**Acceptance checks:** valid aligned/unaligned payloads work where permitted; null, unmapped, kernel-space, read-only output, and page-crossing buffers fail safely; ordinary libc terminal detection still works; the shell survives every negative case.

Reproduction: raw Linux x86-64 `ioctl(0, TCGETS, NULL)`, probe 27.

Expected: `-EFAULT`.

Observed: `KERNEL PANIC: cast causes pointer to be null`, in `dev.TTY.ttyIoCtl`. The TCGETS branch converts `arg` directly into `*linux.termios`.

Source: `kernel/src/dev/TTY.zig:325` and the ioctl syscall handler.

Log: `/tmp/lazyos-general-tests/null-ioctl-full/serial.log`.

### 2. User SIMD register contents change across a syscall

**Severity: Critical correctness issue · Priority: P0 · Effort: Medium–large**

**Description and impact:** XMM0 changes during a syscall that has no reason to alter user SIMD state. Compilers and libraries use these registers for more than floating-point arithmetic, including ordinary copies. Consequently, valid programs may calculate wrong results or crash depending on timing and code generation. This is a systemic context-preservation problem, not just a getpid implementation error.

**Fix scope:** establish a coherent x86 extended-state policy for syscall entry/exit, interrupts, and task switches. Account for kernel-generated SIMD instructions, per-task state ownership, required buffer alignment, CPU features, and initialization. Preserving a single XMM register is not a complete solution; disabling generated kernel SIMD alone is also insufficient to support multiple user tasks using SIMD.

**Acceptance checks:** the original XMM0 probe passes; test additional XMM registers, x87 state, and enabled AVX state as applicable. Exercise timer interrupts and switches between tasks holding different patterns, plus nested entry paths. Retest with the kernel's actual compiler options.

Reproduction: load XMM0 with two known 64-bit values, invoke raw syscall 39 (`getpid`), then compare XMM0 with the original values, probe 30.

Expected: unchanged user SIMD state.

Observed: mismatch. Probe emitted failure marker syscall 62301. The same probe exits successfully on the Linux host. Kernel assembly generated by Zig uses XMM registers, but syscall/interrupt context handling does not preserve SIMD state.

Source: `kernel/src/arch/arch.s` and context-switch handling.

Log: `/tmp/lazyos-general-tests/extra-full/serial.log`.

This demonstrates register corruption; it does not establish that SIMD corruption caused every earlier logging-sensitive failure.

### 3. Malformed ELF input panics the kernel

**Severity: High · Priority: P1 · Effort: Medium**

**Description and impact:** Loader code trusts segment sizes before performing arithmetic. A file claiming more bytes on disk than it needs in memory causes arithmetic failure in privileged code. Malformed input should be rejected before allocations, copies, or mapping changes. Only the filesz/memsz case was reproduced here; the full ELF input space was not fuzzed.

**Fix scope:** validate program-header bounds and sizes, filesz <= memsz, checked additions and rounding, file offsets, supported ELF types, valid user segment ranges, overlaps, reserved addresses, and an appropriate entry point. Clean up partial allocations on rejection or allocation failure.

**Acceptance checks:** reject the included malformed file without a panic or persistent frame leak. Also test truncated headers/segments, overflowing fields, addresses outside user space, unsupported dynamic executables, and repeated load failures. Existing hello and static Coreutils executables must still load.

Reproduction: modify a valid static executable's first PT_LOAD header so p_memsz is 1 while p_filesz remains larger, then execute `run badelf`.

Expected: reject the executable and return to the shell.

Observed: `KERNEL PANIC: integer overflow` in `Process.loadElf`. The loader does not reject filesz > memsz before its segment arithmetic.

Source: `kernel/src/proc/Process.zig`, especially PT_LOAD validation and the filesz/memsz subtraction.

Log: `/tmp/lazyos-general-tests/malformed-elf-full/serial.log`.

### 4. Sparse Ext2 executable causes a short read and kernel panic

**Severity: High · Priority: P1 · Effort: Medium**

**Description and impact:** A zero block pointer inside a sparse regular file represents logical zero bytes, not end-of-file. The reader stops prematurely, so a valid file cannot be read completely. The higher-level readAlloc function then turns the short read into a kernel panic. These are two related defects: incorrect filesystem semantics and fatal handling of a recoverable read condition.

**Fix scope:** return zero-filled data for sparse ranges while advancing the file position and continuing into later allocated blocks. Audit direct and indirect block handling. Make readAlloc accommodate valid short reads or return an ordinary error on unexpected EOF rather than panic.

**Acceptance checks:** read holes at the beginning, middle, and end; verify byte-for-byte contents and file-position updates; test buffers spanning hole boundaries and indirect-block ranges. Execute a valid sparse ELF successfully, and verify real I/O errors are propagated safely.

Reproduction: add the valid static probe executable to an Ext2 image with debugfs, preserving zero-filled file regions as sparse holes; execute `run kprobe 1`.

The file was verified by dumping it back out with debugfs and comparing the bytes with the original. Its inode contains holes between allocated blocks.

Expected: holes read as zeroes; a filesystem read failure must not panic the whole kernel.

Observed: Ext2 stops at the first hole; the executable-read path panics with `SIZE MISMATCH: UnexpectedEOF`.

Sources: `kernel/src/fs/Ext2.zig:795` and `kernel/src/fs/File.zig:48`.

Log: `/tmp/lazyos-general-tests/main/serial.log`.

The remaining tests used a temporary filesystem built without sparse holes to avoid stopping the suite at this bug.

### 5. Shell command run without arguments panics

**Severity: Medium · Priority: P1 · Effort: Small**

**Description and impact:** The shell indexes the program-name slice before checking its length. A normal interactive typo therefore becomes a kernel bounds-check panic. Exploitation beyond a local crash was not tested. The immediate fix is small even though input validation should be reviewed across other built-in commands too.

**Fix scope:** check the argument count before accessing args[0], print usage or return a handled command error, and preserve the shell loop. Review neighboring handlers for the same unchecked-index pattern.

**Acceptance checks:** bare run and run followed only by spaces return a useful error; valid run commands still work; missing executables and repeated invalid commands leave the shell usable.

Reproduction: enter `run` with no program name.

Expected: report missing argument or show usage.

Observed: `KERNEL PANIC: index out of bounds: index 0, len 0` in the run handler.

Source: `kernel/src/shell/commands.zig:160`, `args[0]`.

Log: `/tmp/lazyos-general-tests/missing-run-argument-full/serial.log`.

## Passed checks

The main and follow-up result files contain 36 PASS entries, including boot and repeated signal/fault-isolation checks. Coverage included:

- Raw read/write zero-length handling with null buffers.
- Rejection of null, unmapped, and kernel-space read/write pointers.
- Oversized file descriptors rejected by read, write, close, and fstat.
- Invalid nested writev buffers and excessive vector counts rejected.
- Missing paths and null stat paths rejected.
- stat/lstat/fstat agreement for the known regular file (59 bytes).
- Unaligned stat output buffer.
- Anonymous mmap pages initially zeroed and writable.
- Partial unmapping preserves neighboring mappings.
- Repeated unmapping does not double-free a frame.
- Fixed replacement of an owned mmap page supplies zeroed memory.
- Rejection of unaligned, zero-length, overflowing, and upper-bound mapping/unmapping requests used by the probes.
- A read syscall rejects a read-only destination mapping.
- Validation catches a buffer crossing into an unmapped page.
- PROT_NONE reservation denies access and can be unmapped.
- brk growth supplies zeroed memory and can shrink back.
- Basic raw rt_sigaction default/ignore/query handling and overlapping input/output buffers.
- Access after munmap and access to kernel memory fault only the user process; the shell remains usable.
- Ctrl+C terminates a CPU-bound process.
- Ctrl+C interrupts blocked hello reads four times after the earlier three-run regression test.

### Anonymous-memory exit cleanup measurement

After warming up the VM, the population count of the user allocator bitmap was 534929. It remained 534929 after twelve additional process launches, each allocating and deliberately leaving 64 KiB mapped before exit. Cleanup time was allowed before the final measurement.

The count includes unavailable/reserved bits; the relevant result is that it did not increase. This measures user-frame reclamation for this workload, not kernel heap usage or every allocation-failure path.

An initial attempt to read the bitmap failed because of test-harness filename quoting. That result is recorded as INCONCLUSIVE and superseded by the successful retry.

## Utility compatibility observations

**Severity: Medium compatibility gap · Priority: P2 · Effort: Medium–large overall**

These observations are missing interfaces, not evidence that every launched utility is broken. A program may tolerate optional calls such as fadvise64 or try fallbacks. Implement and test the syscall semantics actually needed by the intended utilities; returning a fake success is not a substitute. In particular, newfstatat/statx need path, descriptor-relative, flag, and output-layout semantics beyond the legacy stat handlers.

Acceptance should check actual output and exit status against known files/directories, not only whether a process exits. Prioritize the interfaces needed by the next chosen utility rather than implementing every syscall at once.

Eight existing utilities were launched and returned control without a kernel panic: true, false, echo, cat, pwd, uname, ls, stat. Completion alone does not establish correct output or exit status.

Serial traces show these missing Linux x86-64 syscalls:

| Utility | Missing syscall(s) observed |
| --- | --- |
| cat | 221: fadvise64 (often optional) |
| pwd | 79: getcwd |
| uname | 63: uname; 72: fcntl |
| ls, stat | 262: newfstatat; 332: statx; 72: fcntl |

Implementing legacy stat/lstat/fstat does not cover libc programs using newfstatat or statx. These are compatibility gaps, separate from the kernel panics above.
